## 3. RLS `[CÓDIGO]` + `[SEM AMBIENTE]`

Este sandbox não tem `docker` nem `supabase` (confirmado: ambos ausentes do
PATH) — não há como abrir uma sessão Postgres real e rodar
`has_table_privilege`/`pg_policies` contra um banco vivo, como o
`CHECKLIST_PRONTIDAO_PILOTO.md` registra ter sido feito em 2026-07-09 (commit
`b1f703a`). A prova possível aqui é **estática sobre o SQL real** — o mesmo
arquivo que `supabase db push` aplicaria — não uma citação de que a migration
existe.

Novo teste `src/lib/security/tenancy-rls-migration-proof.test.ts` (17
asserções, todas passando) confere, lendo `supabase/migrations/*.sql` de
verdade via `collectSqlSources()` (já usado por `bun run parity`):

- `organizations`, `profiles`, `waves`, `wave_invites`, `wave_responses`,
  `wave_capsules` têm `ENABLE ROW LEVEL SECURITY`.
- As policies de tenant (`waves_org`, `capsule_org`, `waves_admin_write`,
  `profile_own`) referenciam literalmente `org_id IN (SELECT org_id FROM
  public.profiles WHERE id = auth.uid())` — não é filtro de aplicação, é
  predicado de banco.
- `wave_responses`: nenhuma migration concede SELECT a `anon`/`authenticated`;
  INSERT/UPDATE/DELETE foram revogados; só `service_role` tem `ALL`.
- `count_wave_responses` e `submit_wave_response`: `SECURITY DEFINER SET
  search_path = public`, `EXECUTE` revogado de `PUBLIC` antes de conceder,
  `FOR UPDATE` trava o convite antes de decidir.

**Comportamento por identidade** — usuário autenticado vinculado: lê a
própria org via `waves_org`/`capsule_org` `[CÓDIGO]`. Usuário sem vínculo
(`profiles` vazio): `resolveOrgMembership` retorna `no_profile`, nenhuma
função privilegiada prossegue `[CÓDIGO]` (`authorize.server.test.ts`). Service
role: bypassa RLS por desenho, único caminho para ler `wave_responses` bruta,
sempre atrás de `authorizedOrgId` checado ANTES da leitura
(`capsule-aggregator.server.ts:59-61`) `[CÓDIGO]`.

**Achado (P1, não corrigido nesta prova):** `listOrgWaves`/`listOrgCapsules`
(`db-adapter.ts`) usam o client `@/integrations/supabase/client` — o mesmo
singleton do navegador, `storage: typeof window !== 'undefined' ? localStorage
: undefined`. No servidor, `window` é `undefined` → nenhum
`.auth.setSession()`/token é anexado antes da consulta. Nenhum arquivo chama
isso. Resultado: nestas duas funções, o predicado `auth.uid()` das policies
`waves_org`/`capsule_org` nunca resolve para o usuário real no contexto de
servidor — a proteção efetiva hoje é o filtro de aplicação `.eq("org_id",
orgId)` (com `orgId` corretamente vindo da sessão via `requireOrgAdmin`, nunca
do payload), não a policy de RLS em si. Não é uma fuga cross-tenant (o filtro
de app está correto e testado agora), mas é uma camada a menos do que a
tabela sugere, e diverge do padrão-ouro de `submit_wave_response`/
`capsule-aggregator`. Registrado para investigação própria — fora do corte
mínimo desta prova (exigiria decidir como propagar o `access_token` da sessão
para um client por-requisição, mudança de arquitetura maior que "modo
enxuto" comporta aqui).

## 5. k≥5 `[CÓDIGO]`

`K_ANONYMITY_MIN = 5` em `capsule-aggregator.server.ts:15`, único portão de
publicação (nunca de fechamento — fechar sem atingir o limiar sela a onda sem
cápsula, honestamente). Coberto por `capsule-aggregator.server.test.ts`
(preexistente): `n=3` recusa (`below_k_anonymity`, nada escrito); `n=5`
(default do fixture) agrega; `n=12` (>5) atualiza a cápsula via upsert.
`wave_responses` não tem `org_id` — cada wave pertence a exatamente uma org
(FK fixa), então misturar respostas de dois tenants para atingir o limiar é
estruturalmente impossível, não apenas evitado por lógica (não há consulta em
nenhum lugar do repo que agregue `wave_responses` por mais de um `wave_id`
simultaneamente). Nunca se afirma "anonimato garantido" em nenhuma string do
produto (grep dirigido, zero ocorrências fora deste documento técnico).

## 11. Q1.1B — autorização dinâmica corrigida; ambiente real BLOQUEADO

Executado em 2026-07-24, mesma branch/worktree.

**Autorização server-side (fechado, `[CÓDIGO]`).** `listOrgWaves`/
`listOrgCapsules` (`db-adapter.ts`) agora exigem `accessToken` + `orgId` e
