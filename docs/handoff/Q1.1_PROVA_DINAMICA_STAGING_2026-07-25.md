## 1. Ambiente `[VIVO]`

Projeto Supabase **externo ao Lovable**, criado pelo founder especificamente
para esta prova. O Lovable Cloud é 1 projeto ↔ 1 backend gerenciado, sem
multi-env nativo — por isso o staging vive fora dele, e o projeto de produção
(`shlmzz…`) **não foi tocado em nenhum momento**: nenhuma leitura, escrita,
migration ou credencial de produção foi usada nesta sessão.

| Item | Valor |
|---|---|
| Projeto | `vitalos-staging` (org própria do founder, plano Free) |
| Isolamento | projeto separado, credenciais próprias, zero dado real |
| Aplicação das migrations | via SQL Editor do painel (sem Docker/CLI neste ambiente) |
| Migrations aplicadas | as 40 de `supabase/migrations/` @ `0a9fdb5`, em ordem |
| Resultado | **29 tabelas** criadas, **29 com RLS ativo** (conferido por query) |

Ajuste necessário só para a aplicação em lote (não altera o repo): 4 policies
(`response_submit`, `own_card_state`, `own_events_select`, `own_events_insert`)
são declaradas em mais de uma migration, e a constraint
`wave_capsules_wave_id_unique` em duas. Aplicadas uma a uma pelo CLI isso não
falha; concatenadas num único script, sim. Resolvido com `DROP … IF EXISTS`
antes de cada `CREATE POLICY` no script combinado — **as migrations do
repositório não foram modificadas.**

## 2. Método da prova dinâmica

Sessões de usuário real simuladas no próprio Postgres, com o mecanismo oficial
do Supabase — `SET LOCAL ROLE authenticated` + `SET LOCAL "request.jwt.claims"`
— o que faz `auth.uid()` responder exatamente como responderia numa requisição
HTTP autenticada, que é a função usada por todas as policies. Confirmado antes
de tudo: `SELECT auth.uid()` devolveu o UID simulado. Todo teste roda dentro de
`BEGIN … ROLLBACK`, então nenhuma tentativa (inclusive as de escrita) deixou
estado no banco.

## 5. k≥5 `[VIVO]` / `[CÓDIGO]`

- n=4 → nenhuma cápsula existe. n=5 → cápsula publicada. n=7 → só agregado
  (`participant_count`, `dimensions`), nunca resposta individual. `[VIVO]`
- Respostas de A nunca completam o limiar de B: `wave_responses` não tem
  `org_id`; cada `wave_id` pertence a exatamente uma organização por FK, e
  nenhuma consulta do repo agrega mais de um `wave_id` por vez. `[CÓDIGO]`
- `wave_responses` permanece sem nenhuma policy de SELECT — confirmado
  intencional (comentário da migration `20260705160043`: *"Deliberately NO
  SELECT policy"*). O único leitor é o service role, dentro de
  `capsule-aggregator.server.ts`. `[VIVO]` + `[CÓDIGO]`

## 6. Dois achados reais — descobertos, corrigidos e reconferidos `[VIVO]`

Ambos são invisíveis para análise estática: o texto das migrations está
"correto", o privilégio real no banco é que divergia. São exatamente o tipo de
coisa que justificou exigir a prova dinâmica.

### 6.1 P2 — `wave_responses` com SELECT concedido a `anon` e `authenticated`

`has_table_privilege` devolvia `true` para os **dois** papéis de cliente, sem
que nenhuma migration conceda isso em texto: vem do default de privilégio da
conta. A tabela foi criada em `20260630161949`, antes da disciplina de `REVOKE
ALL` explícito adotada a partir de `20260705100000`; a migration que depois
endureceu a tabela (`20260705160043`) revogou `INSERT/UPDATE/DELETE` e
**esqueceu `SELECT`**.

Não era vazamento ativo (sem policy de SELECT, o RLS nega por padrão) — mas era
a única coisa entre uma policy de SELECT futura e a exposição de resposta
individual. Este repo já documentou o scanner do Lovable adicionar `GRANT` por
conta própria (`20260705160043`, `20260714130000`), o que torna o risco
concreto, não hipotético.

Correção `20260725120000_revoke_wave_responses_select_grant.sql`; após aplicar
em staging, ambos os papéis voltaram `false`. ✅

### 6.2 P1 — `count_wave_responses` sem vínculo de tenant

A função só contava por `wave_id`, **sem verificar organização nenhuma**, e tem
`GRANT EXECUTE TO authenticated` (necessário para o painel de ondas). Qualquer
usuário autenticado de qualquer organização podia chamá-la com o `wave_id` de
outra organização — inclusive direto pelo endpoint REST
(`/rest/v1/rpc/count_wave_responses`), sem passar pelo app — e obter a contagem
exata de respostas alheia.

Confirmado ao vivo: usuário do Tenant A obteve **7**, a contagem real da onda do
Tenant B. Vazamento de metadado (contagem), não de conteúdo — mas explorável
naquele momento, sem depender de nenhuma condição futura.

Não era explorado pelo app real: os dois chamadores
(`capsule-aggregator.server.ts`, `wave-admin.functions.ts`) usam service role e
já verificam a organização antes. A função é que não tinha trava própria.

Correção `20260725130000_scope_count_wave_responses_to_caller_org.sql` —
reintroduz o mesmo vínculo que as policies usam, com bypass para `service_role`.
Reconferido em staging: **4** na onda própria (correto), **0** na onda alheia
(fechado), **7** via service role (uso interno preservado). ✅

Ambos ganharam asserção no gate (`tenancy-rls-migration-proof.test.ts`), para
que a regressão falhe o build — não dependa de outra auditoria manual.

## 7. Provisionamento `[VIVO]`

O checklist do documento anterior foi executado de ponta a ponta, duas vezes
(um tenant cada), nesta ordem: criar organização → criar responsável
(`profiles` com papel admin) → vincular usuário → criar ciclo/onda → validar
RLS (§4) → validar k≥5 (§5) → validar acesso (§4) → registrar evidência (este
documento) → limpeza (§9). Responsável pela execução: founder (painel) +
Claude Code (SQL/validação). Passo "configurar unidades/grupos" segue sem
aplicação: não existe conceito de sub-unidade dentro da organização neste corte.

## 9. Limpeza e rollback `[VIVO]`

Todos os testes de leitura/escrita rodaram sob `ROLLBACK` — não deixaram
estado. O que persiste no staging são apenas os dados sintéticos das §3.

```sql

CREATE SCHEMA public;
```

Ou, preservando o schema:

DELETE FROM public.wave_responses;
DELETE FROM public.wave_invites;
DELETE FROM public.waves;
DELETE FROM public.profiles;
