### Histórico formal ausente — e o controle compensatório

`supabase_migrations` não existe no staging (`tem_historico_formal=false`).
Esperado: o schema foi aplicado pelo SQL Editor do painel, que não registra
histórico — só o Supabase CLI o faz. Sem isso, editar uma migration já aplicada
não deixaria rastro detectável.

Controle compensatório desta rodada:

- `supabase/migrations.manifest.json` — identidade SHA-256 de cada arquivo, em
  ordem, versionada junto do código. Hash calculado com CRLF normalizado para
  LF, para ser idêntico em Windows e Linux.
- `rollupSha256` = `496655c9bc68…` — um único hash sobre todos os hashes em
  ordem; muda se qualquer arquivo mudar, sumir ou trocar de posição.
- `src/lib/schema-parity/migration-manifest.test.ts` — 12 testes que falham o
  build em caso de migration alterada, removida, reordenada, duplicada, vazia,
  sem prefixo de timestamp ou com buraco na numeração.
- `bun run manifest` / `bun run manifest:write` — verificação e atualização.

**Mecanismo canônico daqui em diante:** toda migration nova entra como arquivo
em `supabase/migrations/`, seguida de `bun run manifest:write` no mesmo commit.
O gate falha se o manifesto e os arquivos divergirem. Quando houver Supabase CLI
disponível, migrar para `supabase db push` (que mantém histórico formal) e
manter o manifesto como segunda camada.

## GATE 1 — JWT real `[VIVO]` — **JWT_REAL_PASS**

Harness pronto e versionado: `scripts/staging-jwt-proof.ts`
(`bun run staging:jwt-proof`). Typecheck limpo; bloqueia com exit 2 e instrução
clara quando faltam credenciais.

O que ele prova, sem simulação — Supabase Auth (`signInWithPassword`) → JWT real
→ PostgREST por HTTP → `auth.uid()` → policy de RLS → isolamento por tenant.
Diferença para a prova anterior: lá as sessões eram simuladas no Postgres
(`SET LOCAL ROLE` + `request.jwt.claims`), o que exercita a policy mas **não**
exercita emissão/validação de token nem o caminho HTTP.

Cenários cobertos: usuário A (tenant A), usuário B (tenant B, simétrico),
usuário sem membership, sessão inválida (token forjado) e `anon` sem sessão.
Para cada um: `auth.uid()` correto, leitura/listagem/escrita no próprio tenant,
recusa de leitura/listagem/escrita no tenant alheio, `org_id` alheio no payload
não concedendo acesso (WITH CHECK), e RPC de contagem não vazando onda alheia.

Salvaguardas: aborta se a URL apontar para produção; nunca imprime token, senha
ou chave; senhas aleatórias só em memória; credenciais em `.env.local`
(confirmado gitignored via `git check-ignore`); limpa ao final o que criou.

Nota de compatibilidade: o `vitalos-staging` usa o formato NOVO de chaves
(`sb_publishable_…` / `sb_secret_…`), que são strings opacas, não JWTs. O
`supabase-js` envia a chave também como `Authorization: Bearer <chave>`, o que
o GoTrue rejeita nesse formato. O harness aplica o mesmo tratamento que
`src/integrations/supabase/client.server.ts` já faz no app real (remove o
header quando a chave é opaca) e aceita as duas nomenclaturas de variável.

### Resultado — 26/26 cenários PASS

| Cenário | Identidade | Operação | HTTP | Linhas | Regra |
|---|---|---|---|---|---|
| autenticação emite JWT válido | usuário A | POST /auth/v1/token | 200 | 1 sessão | Supabase Auth |
| `auth.uid()` corresponde | usuário A | GET /profiles | 200 | 1 | policy `profile_own` |
| lista o próprio tenant (sem filtro) | usuário A | GET /waves | 200 | 3 | policy `waves_org` |
| não lista o tenant alheio | usuário A | GET /waves?org_id=eq.\<outro\> | 200 | 0 | policy `waves_org` |
| não lê onda alheia sabendo o id | usuário A | GET /waves?id=eq.\<alheia\> | 200 | 0 | policy `waves_org` |
| escreve no próprio tenant | usuário A | PATCH /waves (própria) | 200 | 1 | policy `waves_admin_write` |
| não escreve no tenant alheio | usuário A | PATCH /waves (alheia) | 200 | 0 | policy `waves_admin_write` |
| **orgId alheio no payload NÃO concede acesso** | usuário A | POST /waves (org_id forjado) | **403** | 0 | `waves_admin_write` (WITH CHECK) |
| RPC de contagem não vaza onda alheia | usuário A | POST /rpc/count_wave_responses | 200 | 0 | `count_wave_responses` org-scoped |

final as ondas que criou.

O caso mais relevante é o **403 no `org_id` forjado**: o usuário A declarou
explicitamente `org_id` do tenant B no corpo do INSERT, e o `WITH CHECK` da
policy recusou no banco. É a prova direta, por HTTP real, de que `orgId` no
payload não autoriza — a mesma afirmação que a Q1.1B só havia sustentado por
teste de unidade.

incerteza é, por si só, o problema. Antes do piloto, é preciso obter do Lovable
a política real (frequência, retenção, PITR, procedimento de restauração e de
exclusão) e nomear um responsável operacional.
